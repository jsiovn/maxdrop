# LookAt Constraint with an animated target weight Implementation Plan

> **For agentic workers:** Use subagents when appropriate to implement this plan. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A synthetic test proves a LookAt Constraint resolves its targets (and up node) to the right nodes when a
target weight is animated, and that the weight takes its controller's saved value or the documented fallback.

**Architecture:** Test only: `maxdrop/reader/controllers.py` already reads an `Animated` weight through
`self.scalar(w.index, 1.0)` and `maxdrop/reader/pblock.py` gives block references and controllers one slot sequence
in entry order (maxdrop-em3.20). The weight table (id 0) comes before the targets (1) and `pickUpNode` (9), so a
controller of a weight takes slot 0 and every target moves up by one. The test helpers learn to write a weight
element as a controller (tag `0x80`, as `list_block` does for list weights); a new test pins the matrices against
the same scene with plain weights (themselves pinned to 3ds Max 2020 probes by `test_weighted_targets_in_a_file`
and `MAX_CONSTRAINT`). docs/FORMAT.md's LookAt Constraint rows point to the shared slot sequence.

**Tech Stack:** plain Python `unittest`; Blender 4.2 / 4.5 / 5.2 headless smoke (no reader code changes, run for the
required build-and-test).

Bead: maxdrop-em3.98

Lane (maxdrop-6n0.4, code lane): no 3ds Max, no fixture, no oracle. The optional fixture with an animated
constraint weight is left out: unmeasured in 3ds Max is what tag 3ds Max 2020 writes for an animated constraint
weight element (taken as `0x80`, the list-weight form the corpus shows) and that its controller is saved in the
constraint block's slot 0 (the rule em3.20 measured on materials, applied here by entry order).
