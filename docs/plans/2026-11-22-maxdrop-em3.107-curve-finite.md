# Curve Coordinates Past Single Precision Implementation Plan

> **For agentic workers:** Use subagents when appropriate to implement this plan. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A shape whose curve points, handles, section corners or bevel depth do not fit Blender's single
precision (inf, NaN, or past the largest float32) never reaches Blender: the shape is refused or the section /
bevel left out, each with an issue.

**Architecture:** `convert/scene.py curve_description` checks, after the offset and meters are applied, every
point, left and right handle against `lights.MAX_FLOAT` (the largest float32; `abs(c) < MAX_FLOAT` is false for
inf and NaN too). Out of range: it raises `CurveError` (a `ValueError`); `_curve` catches it and the node becomes
an EMPTY placeholder with the issue, as a primitive whose sizes give points past the float range
(`convert/primitives.py`). The refusal is cached per curve key (base, offset), named on the first node only, as a
refused mesh is. A rectangular section whose corners do not fit is not drawn (an issue, like a width of 0); a
round bevel whose depth does not fit is not drawn (an issue). The curve itself stays.

**Tech Stack:** plain Python (no numpy in `curve_description`: the `Curves` tests run without it).

Bead: maxdrop-em3.107. Lane: code (no 3ds Max, no fixture change).

## Findings

- `reader/shapes._ngon` with radius 1e308: 6 sides gives float64-finite knots up to 1.15e308 (inf in float32);
  3 sides gives inf/NaN knots (`r / cos(60 deg)` = 2e308); nothing raises. A corner radius 1e308 on 10 units
  gives 9e307. So the check must be the float32 range, not `math.isfinite`.
- `_straight` (`x + (y - x) / 3`) can overflow on handles even when both points are finite: check after it.
- Meshes: a primitive refuses (placeholder + issue); `extrude` refuses past float32 max. Stored Editable Mesh /
  Poly positions have no such check in `mesh_description`: out of this bead's scope (follow-up debt bead).
