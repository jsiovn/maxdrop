# Reader-defect net names AttributeError Implementation Plan

> **For agentic workers:** Use subagents when appropriate to implement this plan. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An AttributeError raised while reading a `.max` (`ops._read_scene`, `ops._preflight`) is reported as a
file not imported, with its traceback in the console, like a TypeError or KeyError, instead of ending the operator.

**Architecture:** `ops._DEFECTS` becomes `(TypeError, KeyError, AttributeError)`; the comment at it records the
decision and why the net stays narrow. The fuzz harness stays strict (its reader path has no net), its test now
proves all three types escape there. `tests/blender/run.py check_reader_defect` gains an AttributeError case, which
is the red check.

**Tech Stack:** Python 3.11+, Blender 4.2 / 4.5 / 5.2 headless.

Bead: maxdrop-em3.94

---

## Decision

Add AttributeError.

- It is as likely a reader defect as a TypeError: an attribute read on `None` (a chunk walker that found no child,
  a missing reference) or a typo. The reader never raises it for a damaged file: damage is `MaxFileError`.
- The one AttributeError raised on purpose in reader/convert is `convert.primitives.Params.__getattr__` for a
  missing key; `params_of` fills every key of the class's spec (stored value or default), so a miss there is a
  code defect, not the file's.
- `_read_file` touches no Blender data, so a bpy AttributeError cannot be mistaken for a reader defect.
- Not wider (not `Exception`): `NameError`, `ZeroDivisionError` and others stay escapes so that the fuzz campaign
  and the console show them; the net names the types a defect of reading untrusted structure most often raises.
  The fuzz campaign found 0 escapes of any type: this is a fallback, not a fix of a known case.
