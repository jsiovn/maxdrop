# Linear color images in Linear Rec.709 Implementation Plan

> **For agentic workers:** Use subagents when appropriate to implement this plan. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A color-input image the converter reads as linear (gamma 1.0) or decodes with a Gamma node (an override
other than 2.2) is loaded in the `Linear Rec.709` color space, not Non-Color, so Blender converts its sRGB-primaries
pixels into the scene's working space; data inputs stay Non-Color.

**Architecture:** The builder sees only a `texmaps.Image` (no input kind), and data images carry a gamma too (a
float-file roughness map, a mask), so it cannot tell a linear color image from a data image. The decision therefore
stays where it already is, `texmaps.colorspace(kind, gamma)`: for COLOR with a gamma other than ~2.2 it returns a new
constant `LINEAR = "Linear Rec.709"`. The builder resolves that name against the input color spaces of the running
Blender (OCIO config) and falls back to Non-Color when it is missing (a custom config); the resolved name is the image
reuse key and the name set on the image. The Gamma-node predicate compares with `LINEAR` instead of `NON_COLOR`.
Touches `maxdrop/convert/texmaps.py` as well as the bead's `maxdrop/build/materials.py` (texmaps is in the bead's
Read list: the color-space rule lives there).

**Tech Stack:** Python 3.11 syntax, Blender 4.2 / 4.5 / 5.2 (all three ship `Linear Rec.709` in the stock config,
probed 2026-11-19).

Known approximation: an override other than 2.2 is decoded by a Gamma node after the image node, so in a non-Rec.709
working space the primaries conversion comes before the power curve (exact for the default working space, and for
neutrals in every D65 space). Better than Non-Color, which applies no primaries conversion at all.
