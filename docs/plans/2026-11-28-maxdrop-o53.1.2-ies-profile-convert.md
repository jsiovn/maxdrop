# IES profile, the convert side: Implementation Plan

> **For agentic workers:** Use subagents when appropriate to implement this plan. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every light that names an IES file (a photometric web light, a VRayIES) carries its profile in the scene
description (`LightDescription.profile`), so maxdrop-o53.1.3 can give it the file's distribution.

**Architecture:** `convert/ies.py`'s `parse()` keeps, besides the flux, the validated text, the peak and nadir
candela (times the multiplier), the share of the flux above the horizontal, and what o53.1.9's watts rule needs
(the ballast-lamp factor, the horizontal angles). `Lookup.found()` also gives the base name of the file found.
`convert/lights/reading.py` runs the lookup for every VRayIES and for photometric web lights, and reads the web's
X, Y, Z rotation (block 3, parameters 1 to 3, as stored); `families.py` sets `LightDescription.profile` to a
`Profile(file, photometry, rotation)` or None. Issue lines, kind, cone and power stay as they are.

**Tech Stack:** plain Python (no bpy), unittest.

Base: `304b505`.

## Decisions

- `Photometry.text` is a str: the bytes parse() validated, up to the end of the candela table (numbers past it are
  never read, so never handed on), decoded as Latin-1 (one character per byte: lossless; Blender's Text takes str).
- Peak = the table's largest candela x the multiplier; nadir (x the multiplier): type C the mean of the planes at
  vertical 0 (0 when the table starts past 0: Blender gives 0 before the first angle, measured in o53.1.9); types A
  and B the candela at vertical 0, horizontal 0 (the axis V-Ray aims down, "VRayIES type A and B ranges, measured"),
  linear between angles. Up share: type C the flux above vertical 90 (the zones split at 90) over the flux, the same
  planes and symmetries; types A and B 0 (V-Ray renders only |H| <= 90, the front hemisphere); 0 for a flux of 0.
- Extra fields beyond the bead's list: `ballast_lamp` and `horizontal` (a tuple of the file's horizontal angles):
  o53.1.9's watts rule (docs/FORMAT.md) divides by the ballast-lamp factor and by 35/32 or 17/16 by plane layout.
- `Profile` is a namedtuple `(file, photometry, rotation)` with properties `text`, `peak`, `nadir`, `flux`, `up`
  (delegated): one Photometry per file shared, the record stays small. A VRayIES's rotation is (0, 0, 0).
- The web rotation is read without issue lines (an animated one: 0.0, silent): it is not applied in this bead
  (o53.3.5 does, and reports it then); reading it through `_PHOTOMETRIC_PARAMS` would add "parameter block 3 is
  missing" lines. Values as stored (the unit is measured by the max lane, o53.2.7).
- The lookup for a photometric light runs for the distributions describe() turns into a web spot (not isotropic,
  spot or diffuse), as `_describe_photometric` does.
- No extra cache in `Lookup`: `TextureIndex.find` caches by (path, resolved) and `Lookup` reads each found path
  once; the fixture test counts `ies.read` calls (one), not index calls.
- Not measured, said in docs/FORMAT.md, a code comment and the bead notes: types A and B's nadir, up share and peak
  in Blender; the nadir 0 of a type C table that starts past 0 (as Blender's node gives it, measured in o53.1.9, not
  in V-Ray); the rotation's stored unit. Types A and B's peak counts only the planes V-Ray renders (-90 to 90; type A
  from 0 to 90: 0, as its flux).
- The scene's share of the texture walk has its own found and missing counts (not reported); a web light's lookup
  can walk a rule no texture walked before, so a stopped walk can now show in the report's texture-search line: the
  walk the bead's Risk accepts.
- Up share clamped to [0, 1].
- The VRayIES flux and its issue lines keep using `photometry` / `photometry_issue` only with override off and power
  above 0, as today; for every other light a file not read or not found gives profile None and no new line.
